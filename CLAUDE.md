# Project: FinBase

## What this is
FinBase is a loan management system for small private moneylenders in
Tamil Nadu, India.
They currently run their business on paper ledgers. The app digitises loan
origination, repayment tracking, collateral records, and business expenses.

One differentiating feature: a shared cross-company registry that lets any
financier check whether a vehicle is already pledged as collateral with
another financier on the platform. Everything else is private per company.

## Who uses it
Small lending businesses — typically 1 to 5 people, often one owner plus a
couple of staff. Low technical sophistication. Android phones in the
₹8,000–15,000 range. Intermittent connectivity. Tamil and English.

**There is ONE shared login per company.** No user accounts, no roles, no
permissions, no approval workflows, no maker-checker. The owner, manager and
staff all use the same credentials. Do not invent role-based access control.

## Stack — do not substitute
- Backend: Java 21 (LTS), Spring Boot 3.3+, Spring Web (MVC, not WebFlux),
          Spring Data JPA + Hibernate 6, PostgreSQL JDBC driver, Flyway
- Database: PostgreSQL 16 with Row Level Security
- Scheduling: Spring @Scheduled + ShedLock (no Celery, no separate
          worker/beat process — jobs run in the same app)
- Cache: Redis 7 — OTP storage and rate-limit counters ONLY, not a job queue
- PDF: openhtmltopdf + Thymeleaf templates, server-side only
- Web: React 19 + TypeScript + Vite + TanStack Query + TanStack Table
       + Tailwind + shadcn/ui + React Hook Form + Zod
- Mobile: React Native via Expo managed workflow (Expo Go, NOT Dev Client),
          Expo Router, NativeWind. Android only.
- Storage: AWS S3 ap-south-1
- Shared: TypeScript package, types generated from the OpenAPI spec
          (springdoc-openapi's /v3/api-docs)

Do not add: Redux, an ORM other than Spring Data JPA/Hibernate, headless
Chrome/Puppeteer-equivalents for PDF, Elasticsearch, WebSockets, GraphQL,
Firebase, Auth0, Quartz (ShedLock covers our scheduling needs — don't add
the heavier option), Lombok's `@Data` on JPA entities (causes recursive
toString/equals/hashCode and lazy-loading surprises — `@Getter`/`@Setter`
only, or plain records for DTOs), or any state library beyond TanStack
Query plus React state. If you think something extra is needed, say so and
ask before adding it.

## Domain facts you need

**Four loan types**, each with its own detail table:
personal, vehicle, gold, document (land/property).

**Loans have no approval workflow.** A created loan is immediately ACTIVE.
Statuses: active, closed, foreclosed, seized, written_off.

**Three interest schemes.** Rates are quoted PER MONTH by default.

Scheme A — monthly interest only, principal as a bullet at maturity (DEFAULT):
    monthlyInterest = principal * (monthlyRate / 100)
    installments 1..n-1 : due = monthlyInterest
    installment n       : due = monthlyInterest + principal

Scheme B — flat-rate EMI:
    totalInterest = principal * (monthlyRate/100) * tenureMonths
    emi = (principal + totalInterest) / tenureMonths
    principalComponent = principal / tenureMonths  (same every month)
    interestComponent  = totalInterest / tenureMonths

Scheme D — daily/weekly fixed collection:
    dailyInterest = principal * (annualRate/100) / 365
    or a fixed daily amount for N days

There is NO reducing-balance scheme. Do not implement one.

**Penal charge is either a percentage or a fixed amount**, chosen per loan:
    percentage:   overdueAmount * (pct/100) * (daysOverdue - grace) / 30
    fixedAmount:  a flat rupee figure per overdue installment
Default grace period: 5 days.

**Payment appropriation order:** penal → charges → interest (oldest first)
→ principal → excess.

**Due dates** clamp to month end. Disbursed on the 31st means due on the
28th/29th/30th in shorter months, never rolling into the next month.

**No notifications.** No SMS to borrowers, no push, no email, no reminders.
The only SMS in the system is the login OTP. Do not build a notification
system, a template engine for messages, or a dispatch queue.

**No offline mode** in v1. Do not add SQLite, sync queues, or optimistic
offline mutations on the mobile client.

**PDF download, not printing.** Users download PDFs and print locally if
they want. All PDFs are generated server-side with openhtmltopdf and
returned as a download URL. Never generate PDFs client-side.

**No Aadhaar number is stored anywhere.** Only an uploaded photocopy, kept
in the documents table with category 'aadhaar'. Customer deduplication uses
PAN and mobile number only — deterministic, no fuzzy matching.

**Customers are never deleted.** Only marked inactive.

## Code style
- Java: Checkstyle + SpotBugs clean. Favor records for immutable DTOs.
  Services hold the logic; controllers are thin and never return entities
  directly — always map to a DTO.
- TypeScript: strict mode. No `any`. Types come from the generated OpenAPI
  client — do not hand-write API types.
- Write the test alongside the code, not after.
- Comments explain *why*, not *what*. Skip comments that restate the code.
